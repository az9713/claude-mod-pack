Mods and Hooks Compared

Prepared 2026-10-03 for the reader. Build checked: Claude Code 2.1.288. The mods API is marked "EARLY ACCESS" in its type file and "may change between releases without notice".

Short answer. A classic hook (also called a settings hook) is an action that Claude Code runs when an event happens. The action is a shell command, an HTTP request, a model prompt, an MCP tool call or a subagent. It reads JSON and returns JSON or an exit code.

A mod is a plugin that holds TypeScript functions. Claude Code loads the functions and calls them inside its own process. A mod can do what a classic hook does. A mod can also draw in the interface, keep state, wrap a step with next, and call engine services through $.

Three differences matter most. (1) A mod can draw; the hooks documentation does not describe any way for a classic hook to draw. (2) A command hook starts a new operating-system process for each event; a mod is loaded once and reloads when you save. (3) A mod sits in the chain of a step and can answer for it or rewrite its input; a classic hook returns a verdict.

1. What a classic hook is

You configure it in JSON. The scopes are ~/.claude/settings.json, .claude/settings.json, .claude/settings.local.json, a plugin's hooks/hooks.json (or inline in plugin.json), and the hooks: field in a skill or subagent file. The shape is an event name, a matcher, and a list of actions.

{ "hooks": { "Notification": [
    { "matcher": "permission_prompt",
      "hooks": [ { "type": "command", "command": "...", "timeout": 30 } ] } ] } }

There are five action types. command runs a shell process, sends JSON on stdin, and reads JSON on stdout or an exit code. http posts the JSON to a URL. mcp_tool calls an MCP tool. prompt makes one model call and returns {"ok": true/false, "reason": "..."}. agent (experimental) runs a multi-turn subagent.

For a command hook, exit code 0 continues, exit code 2 blocks with the reason on stderr, and any other code is a non-blocking error. Default timeouts: 10 minutes for command, http and mcp_tool (30 seconds for UserPromptSubmit, 10 seconds for MessageDisplay); 30 seconds for prompt; 60 seconds for agent; 1.5 seconds in total for SessionEnd.

The type file lists 33 classic events: ConfigChange, CwdChanged, DirectoryAdded, Elicitation, ElicitationResult, FileChanged, InstructionsLoaded, MessageDisplay, Notification, PermissionDenied, PermissionRequest, PostCompact, PostModelSwitch, PostToolBatch, PostToolUse, PostToolUseFailure, PreCompact, PreModelSwitch, PreToolUse, SessionEnd, SessionStart, Setup, Stop, StopFailure, SubagentStart, SubagentStop, TaskCompleted, TaskCreated, TeammateIdle, UserPromptExpansion, UserPromptSubmit, WorktreeCreate, WorktreeRemove.

A hook controls behaviour through its output. PreToolUse returns permissionDecision of allow, deny, ask or defer, and may rewrite the tool arguments with updatedInput (the order is not defined when several hooks rewrite the same input). Stop and PostToolUse return decision: "block" with a reason. UserPromptSubmit can add text to the context with additionalContext (maximum 10,000 characters) or block the prompt.

Limits stated in the documentation: a PostToolUse hook cannot undo a tool that has finished. Stop fires each time Claude finishes, not on a user interrupt. A command hook keeps no state between events except in files. A PreToolUse hook runs in every permission mode, so a deny blocks even under --dangerously-skip-permissions; an allow cannot override a deny rule in settings.

2. What a mod is

A mod is a plugin of function hooks. It has three files: .claude-plugin/plugin.json (name, version, description, optional userConfig), hooks/hooks.json ({ "modules": ["./register.tsx"] }), and one TypeScript or JavaScript module that exports register(on, options). The module is an ES module with no require and no import().

Inside register, on(event, matcher?, hook) adds a hook. Every hook has the form ($, e, next):

  • $ is the engine interface. Its nouns are plugin, ui, model, audio, mcp, session, turn, prompt, tool, command, config, telemetry, agent, fs, store, state, clock, http, process, settings and env.
  • e is the event input. It is frozen to every depth.
  • next(e) runs the plugins below this one and then the engine's own behaviour, and resolves to the event result. A hook that returns without calling next answers for itself. next({ ...e, x }) rewrites what the rest of the chain sees. Calling next() with no argument rejects.

The module runs in an environment of its own, with no DOM and no Node. Everything outside it goes through $. The field guide states that a mod runs in Claude Code's own process, needs no Node.js, bundler or build step, and "runs with your permissions" without a sandbox. My reading of the two statements together: the isolated environment limits which APIs the code can see, and $.fs, $.process and $.http then act with your permissions.

Events include tool.call, tool.check, tool.describe, prompt.submit, prompt.compose (system prompt sections), command.run, ui.render, session.start, session.end, turn.start, turn.step (streaming), turn.complete, and every $ call (for example fs.*, store.*, model.*). The classic events are also hookable as classic.<Event>, where e is what the settings hook would receive on stdin.

What a mod can draw

ui.render draws these components: AskUserQuestion, UserMessage, AssistantMessage, ToolUse, ToolResult, ToolGroup, CommandOutput, ToolProgress, Spinner, TurnDuration, InfoNotice, SessionMode, PromptHint, AbovePrompt and Pane. AbovePrompt is the band above the prompt; the engine draws nothing there. $.ui.open opens a Pane. $.ui.toast shows a box in the top right corner (4,000 ms by default). $.ui.status pins one line per plugin under the prompt. The surfaces are terminal, desktop, vscode and mobile; Raster and Image elements exist on the terminal only.

State, config and development

$.state holds session values on the host; they survive a reload and are not written to disk. $.store is JSON on disk and survives sessions (limit 4 MiB). userConfig values come from pluginConfigs in settings.json, and each non-secret field is a row in the /config menu. claude --plugin-dir <folder> loads a mod for one session, and saving a file reloads the module. claude plugin validate <dir> checks it; claude plugin test <folder> runs *.test.ts files.

4. Two examples: a classic hook and a mod hook

Classic hook

A generic example in settings.json. Event PreToolUse, matcher Bash. The script name is a placeholder.

"PreToolUse": [ { "matcher": "Bash",
  "hooks": [ { "type": "command",
    "command": "./scripts/check-bash.sh",
    "timeout": 30 } ] } ]

Claude Code starts check-bash.sh as a separate process for each Bash call and sends the event as JSON on stdin. Exit code 2 blocks the call and sends stderr to Claude. The script has no $, no next and no documented way to draw. The mod hook on the right does the same job for a shell command.

Mod hook

mod-pack/hooks/register.tsx:752-753, shortened.

on('tool.call', { tool: 'Bash' },
  ($, e, next) =>
    guardShell($, options, e.command,
      () => next(e)))
  .catch(($, e, next) => ...)

guardShell reads $.session.cwd(), runs read-only git through $.process.run, and calls $.ui.ask for a Proceed or Cancel dialog. It calls next(e) only after Proceed; otherwise it returns { deny }. The .catch runs if the guard crashes or times out.

A second mod hook in the same file (register.tsx:759-792) hooks ui.render for AbovePrompt. It calls const below = await next(e), then returns a Box that holds {below} plus one row per feature. Keeping below is what stops two mods from overwriting each other's display. This is the fix recorded for token-weather, which first hid next-steps.

5. What mod-pack implements today

The six features, in FEATURES at register.tsx:36: Token Weather (on by default; band row; thunder sound if sound is on), Cache Keeper (on; countdown with a compact button; no model tokens), Prompt Queue (on; /q), Wait What (off by default; the only feature that spends model tokens), Blast Radius (on; dialog only, draws no row), Snake (on; a pane). Slash commands registered at session.start: /mods, /q, /snake. /mods switches features and sound on or off. Features are plain objects of pure functions that never receive $; only register.tsx calls the engine.

6. How they connect

A mod does not replace the classic hooks. It can listen to them. classic.PreToolUse shares the envelope of tool.call. The type file says each classic event fires wherever the engine runs the classic hook, whether or not any settings hook is configured.

Order for a tool call, from the type file: managed-settings hooks run first and their deny is the call's result. Then tool.call and PreToolUse hooks run. Then tool.check fires, and next(e) in it resolves to the engine's verdict (rules, mode, the tool's own check, the PreToolUse decision). A tool.check hook can return any { decision } of allow, ask or deny.

7. When to use which (my recommendation)

  • Use a classic hook when the job is "run this program on that event": a desktop notification, a log line, a formatter after an edit, a simple allow or deny rule. It works in any language and needs no loaded code.
  • Use a mod when the job needs the interface (band, pane, toast, dialog), values kept across events, a wrapper around a step (for example ask, then continue), or a change to the system prompt.
  • Use both when a mod needs to react to a settings-hook event: hook classic.<Event> inside the mod.

8. Limits and gotchas

  • Sound. $.audio.play uses afplay on macOS. A Linux or Windows terminal plays nothing. On Windows, mod sound does nothing by the stated rules. /mods sound on reports the same limit.
  • Panes. A pane opened without a user action waits undrawn below 144 columns (110 for an id the user opened before). A pane opened by a command or button seats at any width.
  • Band size. Size panes and bands to e.props.bodyColumns, not to viewport.columns. The AbovePrompt band is capped at half the terminal rows, prompt included. A height change alone does not redraw.
  • Invalid tree. The engine draws its own component and logs ui.render (<Component>): a hook returned a tree that does not validate.
  • JSX. In a .tsx hooks file a variable named h hides the JSX factory and gives h is not a function.
  • Registration timing. $.tool.register rejects until the session binds, so call it from session.start. A command name equal to a built-in name is refused.
  • Trust. A mod is code that runs with your permissions. Read a mod before you install it.
